# Custom firmware: feasibility and risks

Short answer: **technically possible, but not a quick patch.** It is a real
embedded reverse-engineering project, and on this board it is risky because
there is no published firmware image and probably no way to back up the
original.

## Why the stock firmware is the limit

The LEDs themselves are RGB and individually addressable — the firmware proves
this by lighting a single key in Reactive mode and by sequencing keys in the
wave modes. The limitation is the host protocol:

- The saved LED command is one byte: `(palette_index << 4) | mode`.
- `palette_index` decodes only eight colours (red, orange, yellow, green, cyan,
  blue, purple, white).
- There is one colour for the whole layer. The host cannot address an
  individual LED.
- The animated modes are generated by the MCU from the key matrix. On this pad
  they react to both key-down and key-up; there is no host command to select
  one edge.
- The newer SIKAI per-key RGB table packet was tried on this unit and was
  ignored. The LEDs did not change.
- The host can change the live colour without committing to flash (measured),
  but it still cannot set arbitrary RGB values.

The earlier app tried to fake an in-between colour by rapidly alternating two
palette colours on the host. That looked like strobing, so it has been removed;
the app now exposes only the firmware's eight palette colours and six effects.

## What custom firmware could do

A replacement firmware could implement:

- true per-key RGB and arbitrary colours
- press-only effects (ignore key-up)
- brightness control, custom animations, per-key effects
- the existing USB HID keyboard interface and a new configuration protocol
- on-device profiles and lighting without the app running

The app already has the protocol/backups side and could be extended to speak a
new configuration protocol.

## What the project requires

1. **Identify the exact MCU and LED driver.** Open the case and read the chip
   markings and the LED part number. The family is reported as WCH CH57x
   RISC-V, but the name "CH57x" is ecosystem convention, and some related pads
   use a CH552 (8051). This determines the toolchain.
2. **Find programming/debug access.** WCH parts normally expose a USB ISP
   bootloader and/or a two-wire/SWD debug interface. Look for test pads or a
   header. A WCH-LinkE (or equivalent) is usually needed.
3. **Back up the original firmware.** This is the hard part. The CH57x ISP
   protocol can read *data* flash but not program flash, and read-out
   protection is likely enabled. There is no published firmware image for this
   board. If a backup is impossible, treat any flash attempt as one-way.
4. **Recreate the board support.** USB descriptors (we have them), key matrix
   scan, debounce, layer button, LED driver, storage, and the configuration
   protocol.
5. **Build and flash.** WCH's SDK/MounRiver toolchain, or SDCC if the MCU is a
   CH552. Iterate with a bench supply and a way to recover.
6. **Re-implement the host app's lighting UI** for the new protocol.

## Risks

- **Bricking the pad.** With no firmware backup, a bad flash can leave it
  unusable.
- **Read protection.** The original firmware may not be dumpable at all.
- **Bootloader entry is not a normal feature.** The app deliberately never sends
  `0xEF` (enter ISP); doing so without a recovery plan is a one-way door.
- **Hardware access.** You may need to open the case, solder, or probe pads.
- **Time.** This is a days-to-weeks project, not an afternoon patch.

## Safer alternatives

- Buy a macropad with open firmware (QMK/VIA, RP2040, etc.) for true per-key
  RGB and press-only effects. This is the practical route if those features are
  must-haves.
- Keep this pad for bindings/macros and use its eight palette colours with
  Solid or Off if the release flash is distracting.
- Keep this pad for bindings/macros and use Solid, White or Off if the release
  flash is distracting.

## If you want to pursue it

Recommended next steps, in order:

1. Get a **second identical pad** for development. Do not experiment on your
   only unit.
2. Open the case and photograph both sides of the PCB and the chip markings.
   Do not flash anything yet.
3. Identify the MCU, LED driver, matrix pins, and any debug/ISP pads.
4. Check whether the ISP bootloader is accessible and whether program flash is
   readable. Only then decide whether a safe workflow exists.
5. Build a minimal firmware that enumerates as a keyboard and drives one LED
   before implementing the full feature set.

The repository can host the new firmware and an updated configurator, but that
work should start with hardware identification and a backup strategy — not with
sending the bootloader command.
